# «Альфа Инсайт» (AlfaInsight)

«Альфа Инсайт» — прототип персональной новостной аналитики для руководителей крупного бизнеса, созданный для хакатона Альфа-Банка. Сервис объединяет внешние новости, данные компании и аналитические материалы Альфа-Банка, чтобы отобрать значимые события и объяснить их влияние на конкретную компанию и роль сотрудника.

Одна новость интерпретируется по-разному для различных ролей в принетии решений. Факты, выводы модели и подтверждённая материалами позиция Альфа-Банка показаны раздельно, а каждое утверждение связано с первоисточниками и признаками компании.

> Материалы формируются автоматически, не являются индивидуальной инвестиционной рекомендацией и не отражают официальную позицию банка, если это явно не подтверждено аналитическим материалом Альфа-Банка.

## Для жюри: проверка за 10 минут

1. **Запуск** (нужен только Docker): `cp .env.example .env`, заполнить `JWT_SECRET` и `LLM_API_KEY`, положить CSV кейса в `data/raw/`, затем `docker compose up -d --build` и `docker compose --profile import run --rm importer`. Подробно — в разделе [«Быстрый запуск через Docker»](#быстрый-запуск-через-docker).
2. **Сценарий:** <http://localhost:3000> → регистрация → роль, интересы, компания → «Лента» → новость → «Запустить анализ». Все 11 шагов — в разделе [«Основной сценарий проверки»](#5-основной-сценарий-проверки).
3. **Где что смотреть** — таблица ниже: каждый критерий успеха связан с экраном, кодом и тестом.
4. **Тесты без расхода ключа:** `cd backend && go test ./...`; сквозной тест с PostgreSQL — `TEST_DATABASE_URL=… go test ./internal/server`.

Регистрация открыта, отдельные тестовые учётные записи не нужны. Все компании и персональные данные — обезличенные данные кейса или синтетический holdout (`data/evaluation/`).

### Как анализ отвечает на вопросы качественной интерпретации.

| Вопрос | Блок карточки новости |
|---|---|
| Что произошло? | «Что произошло»: факты со ссылками на новость; предположения — отдельно в «Допущения и ограничения» |
| Почему это важно для этой компании? | «Почему это важно для вашей компании» и «Через какие признаки компании» — механизм через факты `C:*` |
| Какие последствия возможны? | «Возможное влияние на бизнес», «Риски», «Возможности» с вероятностью и горизонтом |
| Какие действия могут быть релевантны? | «Рекомендуемые действия»: что, с чем, кто, когда и почему |
| Как это оценивает банк? | «Как это оценивает Альфа-Банк» — только по материалам банка `R*` |
| На чём основан вывод? | метки у каждого утверждения, «Источники», проверка точности и «Как получен вывод» |

### Ограничения кейса

| № | Ограничение | Как учтено |
|---|---|---|
| 01 | Не лента и не пересказ, а интерпретация с учётом контекста клиента | Механизм влияния через признаки компании, роль как «линза», запрет общих советов, проверка различий по ролям и отраслям |
| 02 | Аналитика банка — заметная часть ценности | Отдельный блок позиции банка, материалы банка в ленте и на «Главной» («Рынок и регулятор»), инструмент поиска по фрагментам |
| 03 | Особенности конкретной компании, а не отраслевые тренды | Факты `C:*`, чувствительности, сведения пользователя о продуктах, рынках и поставщиках; анализ значимой новости без признаков компании отправляется на доработку |
| 04 | Только разрешённые LLM, дневной лимит ключа | Allowlist моделей проверяется перед каждым вызовом ([llm/allowed.go](backend/internal/llm/allowed.go)); дневной бюджет токенов, лимиты частоты и пользовательские лимиты, кэш, модель вызывается только по действию пользователя |
| 05 | Неполные, неоднозначные и зашумлённые данные | Пробелы в данных профиля передаются модели; полнота текста новости; дедупликация; фильтр рубрик; проверка фактов; профиль с неполными данными и шум в holdout |
| 06 | Безопасность AI-компонентов | Разграничение доступа, защита секретов, журнал шагов и инструментов, инструменты только на чтение, изоляция пользовательского текста в промптах — таблица в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#механизмы-безопасности-ai-компонентов) |

## Возможности

- регистрация, вход и ролевой онбординг;
- выбор компании из обезличенного набора данных кейса;
- бизнес-контекст по ОКВЭД, региону, масштабу, группе, банковским продуктам, ВЭД, платежным связям и пользовательским сведениям;
- регулярный сбор официальных RSS-лент, нормализация и дедупликация публикаций;
- локальное предварительное ранжирование Rules + TF-IDF/LSA без вызова LLM;
- пакетная LLM-оценка наиболее релевантных новостей по кнопке;
- многошаговый глубокий анализ новости;
- поиск по материалам Альфа-Банка и связанным новостям;
- риски, возможности и конкретные направления действий;
- проверка ссылок на источники, самопроверка и однократная доработка анализа;
- сверка процентов, сумм, сроков, дат и названий организаций с источниками, доля утверждений с опорой на источники;
- учёт полноты текста новости: только заголовок, заголовок и анонс или полный текст;
- трасса агента с моделями, длительностью и расходом токенов;
- уточняющие вопросы к готовому анализу с ответами по его источникам;
- ИИ-помощник поддержки по работе с сервисом: плавающая кнопка в правом нижнем углу, ответы только по справке с проверкой на выдуманные разделы и кнопки;
- сохранённые новости, обратная связь и аналитические срезы.

## Архитектура

```text
CSV кейса ───────┐
RSS-источники ───┼─→ Go API ─→ PostgreSQL
Аналитика банка ─┘      │
                        ├─→ Rules + TF-IDF/LSA ─→ персональная лента
                        │
                        └─→ агентный LLM-конвейер
                              ├─ классификация
                              ├─ планирование
                              ├─ поиск аналитики и связанных новостей
                              ├─ персональный анализ
                              ├─ детерминированная валидация
                              ├─ проверка чисел, дат и названий
                              ├─ LLM-самопроверка
                              └─ дополнительный поиск и доработка

Next.js ── same-origin /api/* ──→ Go API
```

**Backend:** Go 1.24, chi, pgx, sqlc, goose, Gonum.

**Frontend:** Next.js 16, React 19, TypeScript, Tailwind CSS 4, Radix UI, Motion, Recharts.

**Хранилище:** PostgreSQL 16 в образе pgvector. В текущем ранжировании pgvector не используется: TF-IDF/LSA работает локально в Go.

**API:** OpenAPI-контракт — `backend/api/openapi.yaml`, доступен в запущенном сервисе по `/api/openapi.yaml`.

Интерфейс адаптирован для телефона: нижнее меню, плавающая кнопка поддержки над ним.

**Персонализация анализа** («Личный кабинет» → «Профиль»): «Горизонт планирования» (до 3 месяцев, 3–12 месяцев, больше года) и «Детализация анализа» (кратко или подробно) передаются в промпт; изменение профиля сбрасывает предварительные оценки, а анализ пересчитывается при следующем открытии.

## Как формируется бизнес-контекст

`backend/internal/companies/` преобразует исходные данные в проверяемые факты с идентификаторами вида `C:okved`, `C:region`, `C:has_loan`. Профиль включает:

- основную деятельность и раздел ОКВЭД;
- выручку компании и группы, размер сегмента;
- регион, город, возраст и стадию развития;
- продукты Альфа-Банка;
- страны ВЭД;
- платежные связи и отрасли контрагентов;
- группу компаний и связанные физические лица;
- сведения о продуктах, рынках, поставщиках и приоритетах, добавленные пользователем;
- пробелы в данных и вычисленные чувствительности бизнеса.

## Предварительное ранжирование ленты

До обращения к языковой модели каждая новость оценивается локально:

```text
preliminary_score = min(85, max(rule_score, semantic_score))
```

- `rule_score` учитывает темы новости, отрасль, роль и чувствительности компании;
- `semantic_score` использует TF-IDF, словесные и символьные признаки и LSA;
- LSA строится через воспроизводимый randomized SVD из Gonum;
- модель хранится как неизменяемый snapshot и обновляется атомарно;
- версия корпуса входит в `input_hash`, поэтому оценки пересчитываются после обновления модели;
- если корпуса недостаточно или построение завершилось ошибкой, система продолжает работать только по правилам;
- предварительная оценка никогда не перезаписывает полный LLM-анализ.

Настройки находятся в переменных `SEMANTIC_*`; слой можно отключить через `SEMANTIC_RANKING_ENABLED=false`.

## Глубокий агентный анализ

Анализ запускается пользователем для выбранной новости. Это самописный агент, а не одиночный запрос к модели:

1. **Контекст и кэш.** Загружаются компания, роль и интересы; `input_hash` учитывает статью, профиль, версию промпта и writer-модель.
2. **Классификация.** Быстрая модель извлекает темы, факты, участников, показатели и тип события.
3. **Реестр доказательств.** Основная новость получает ID `A1`, связанные новости — `N...`, материалы банка — `R...`, факты компании — `C:...`.
4. **Планирование.** Агент формирует вопросы, гипотезы и поисковые запросы.
5. **Инструменты.** Go-код выполняет полнотекстовый поиск по аналитике Альфа-Банка и связанным новостям в PostgreSQL.
6. **Черновик.** Модель возвращает строгий JSON: релевантность, влияние, риски, возможности, действия и позицию банка.
7. **Валидация.** Backend ограничивает диапазоны, удаляет неизвестные темы и источники, не допускает неподтверждённую позицию банка и отделяет факты от выводов модели.
8. **Проверка фактов.** Проценты, суммы, сроки, даты и названия из ответа сверяются с реестром источников (см. ниже).
9. **Самопроверка.** Отдельный шаг ищет выдуманные данные, противоречия, неподтверждённые цифры и отсутствие персонализации. Значения, не найденные на шаге 8, добавляются к замечаниям контролёра как серьёзные.
10. **Адаптация.** При серьёзных замечаниях агент выполняет дополнительный поиск и один раз перерабатывает анализ.
11. **Сохранение.** Полный результат, план, классификация, версия промпта и трасса шагов записываются в БД; финальный score обновляет ленту.

### Трасса агента

Под анализом есть блок «Как получен вывод» с пятью вкладками:

- **План** — вопросы, на которые отвечает анализ, гипотезы о механизме влияния, поисковые запросы к аналитике банка и новостям, признаки компании для проверки;
- **Источники** — какие источники использованы и в каких разделах анализа, по какому запросу найден каждый, что найдено, но не использовано, и какие запросы ничего не дали (`result.sources_report`);
- **Признаки компании** — `used_company_factors` с механизмом влияния;
- **Самопроверка** — итог, замечания контролёра с важностью и что изменилось после доработки: оценка, риски, действия, признаки компании, число неподтверждённых значений, покрытие источниками (`result.revision`);
- **Шаги** — каждый шаг с моделью, токенами, длительностью и раскрываемыми деталями: классификация, профиль, план, запросы и найденные материалы, исправления валидатора, проверка фактов, замечания самопроверки.

Скрытые рассуждения модели не сохраняются и не показываются: клиент отбрасывает блоки `<think>`, в трассу попадают только разобранные структурированные результаты шагов. Это проверяется интеграционным тестом.

### Содержательность анализа

Чтобы вывод не сводился к пересказу или общему совету:

- модель возвращает `used_company_factors` — признаки компании `C:*`, на которые опирается вывод, и механизм влияния для каждого («сохранение ставки удерживает стоимость обслуживания кредитов»). Признаки вне профиля и без механизма удаляются; в карточке это блок «Через какие признаки компании»;
- каждое действие содержит объект (что именно), ответственного (роль или подразделение), горизонт и причину. Валидатор удаляет общие советы («следить за развитием ситуации», «оценить потенциальные риски», «проанализировать ситуацию», «принять меры»), действия без объекта или без причины;
- если у значимой новости (релевантность от 40) нет признаков компании, нет конкретных действий или у действия нет ответственного, это становится серьёзным замечанием самопроверки, и агент дорабатывает анализ;
- различия по ролям и отраслям закреплены тестами `internal/agent/personalization_test.go`: одна новость по-разному ранжируется для CFO, руководителя закупок, CEO и главного бухгалтера, а для компаний разных отраслей с разными продуктами получает разные оценки, чувствительности и вход модели. В evaluation считается `differentiation_rate` — доля пар «одна новость, разные компании или роли», где результат различается;
- метрики «С механизмом через признаки», «Конкретных действий», «Удалено общих советов» выводятся в `/analytics/quality`.

Невалидные и обрезанные JSON-ответы не кешируются. Вызовы защищены таймаутами, дневным бюджетом, лимитами частоты и пользовательским почасовым лимитом.

## Уточняющие вопросы к анализу

В карточке новости под готовым анализом есть блок «Спросить об анализе». Пользователь может выбрать быстрый вопрос или задать свой:

| Вопрос | Как отвечается |
|---|---|
| «Почему такая оценка?» | моделью, по анализу и его источникам |
| «Какие признаки компании использованы?» | без модели: признаки `C:*` из выводов и плана и связанные чувствительности бизнеса |
| «Что проверить в первую очередь?» | моделью, по анализу и его источникам |
| «Покажи только подтверждённые факты» | без модели: факты новости, позиция банка и пункты с опорой на источники, без выводов модели |
| свой вопрос (3–500 символов) | моделью, по анализу и его источникам |

Как устроено:

- `POST /api/articles/{id}/analysis/questions` — вопрос, `GET` — история и лимиты;
- анализ ищется строго по паре «статья + текущий пользователь», поэтому спросить о чужом анализе нельзя; `analysis_id` в запросе защищает от вопроса к уже пересчитанному анализу;
- контекст ответа — сохранённый анализ, план агента и реестр источников (`A1`, `N…`, `R…`, `C:…`); валидатор удаляет неизвестные ссылки и помечает тезисы без подходящего источника как вывод модели; если ответа в данных нет, это указывается в поле «Нет в источниках»;
- одинаковые вопросы (без учёта регистра и пунктуации) к той же версии анализа и той же версии промпта берутся из кэша, в том числе у коллеги с идентичным анализом;
- лимиты обращений к модели: `ANALYSIS_QUESTIONS_PER_ANALYSIS` (по умолчанию 10 на анализ) и `ANALYSIS_QUESTIONS_PER_USER_DAILY` (30 за 24 часа); кэш и вопросы без модели лимит не расходуют;
- каждый ответ сохраняется в `analysis_questions` с моделью, версией промпта, токенами и длительностью; токены учитываются в дневном бюджете LLM;
- метки источников в ответе кликабельны и ведут к списку источников этого ответа и к первоисточнику;
- метрики (доля ответов с источниками, кэш, вызовы модели, «нет в источниках», «вне рамок анализа») выводятся в `/analytics/quality`.

## ИИ-помощник поддержки

Кнопка поддержки — круглая, в правом нижнем углу каждой страницы приложения. При первом визите через несколько секунд один раз появляется небольшая подсказка о помощнике; она скрывается сама через 14 секунд или по крестику и больше не показывается. Полноэкранная версия чата — `/support`.

Помощник отвечает только на вопросы о работе сервиса и только по справке (`backend/internal/support/kb.go`, 14 статей):

- **частые вопросы** («Как запустить анализ новости?», «Как сменить роль или компанию?», «Что значат метки…», «Как проверить точность анализа?») отвечаются статьёй справки без модели;
- **свой вопрос:** поиск находит до трёх статей, модель отвечает строго по ним и ссылается на ID статей;
- **проверка ответа модели:**
  - удаляются ссылки на статьи, которые не были найдены, и шаги без опоры на справку;
  - удаляются предложения и шаги с разделами, вкладками или кнопками в «кавычках», которых нет в справке, и с несуществующими адресами страниц;
  - считается доля слов ответа, найденных в процитированных статьях; ниже 55% ответ модели отклоняется и заменяется статьёй справки;
  - вопросы вне темы (инвестиционные советы, новости, личные темы) получают фиксированный ответ, текст модели не показывается;
  - текст вопроса изолирован в промпте от инструкций;
- без ключа модели или после исчерпания лимита помощник отвечает подборкой статей справки;
- проверенный ответ модели на тот же вопрос переиспользуется неделю для всех пользователей; лимит — `SUPPORT_QUESTIONS_PER_USER_DAILY` вопросов к модели в сутки;
- в каждом ответе видно, откуда он: «Из справки», «Ответ ИИ, проверен по справке» или «Справка вместо ответа ИИ»; что убрала проверка, можно раскрыть под ответом;
- все обращения сохраняются в `support_messages`, токены входят в дневной бюджет, метрики — в `/analytics/quality` («ИИ-помощник поддержки»).

## Источники и происхождение выводов

Активные внешние источники:

- РБК;
- Интерфакс;
- ТАСС;
- Ведомости;
- Финмаркет;
- Московская биржа;
- Банк России: пресс-релизы и события.

Для общих лент применяются фильтры деловых рубрик. В базе сохраняются заголовок, анонс, дата, URL и метаданные источника. Материалы Альфа-Банка загружаются из `data/research/` с привязкой к документу и странице.

### Полнота текста

Для каждой публикации БД вычисляет `content_level`:

| Значение | Когда | Как учитывается |
|---|---|---|
| `full_text` | есть полный текст: материал банка, новость добавлена вручную, лента передаёт полный текст и его разрешено хранить | обычный анализ |
| `summary` | заголовок и содержательный анонс | модель не делает выводов о деталях вне анонса; в ограничения анализа добавляется пометка |
| `title_only` | анонса нет или он повторяет заголовок | факты — только из заголовка, важность не выше средней без явных оснований, пометка о предварительном выводе |

Полный текст сохраняется, только если источник сам передаёт его в ленте (`content:encoded`, `yandex:full-text`, Atom `content`) и для источника указано `sources.full_text_policy = 'feed'`. Сейчас это официальные ленты Банка России. Страницы сайтов не скачиваются, платный доступ и защиты не обходятся, для СМИ сохраняются только анонс и ссылка. Полнота показывается в карточке новости и учитывается в промпте.

### Проверка чисел, дат и названий

После ответа модели backend извлекает из анализа проценты, суммы (с учётом «млн/млрд/трлн»), сроки, даты, годы и названия в «кавычках» и ищет их в реестре источников: новости, связанных новостях, материалах банка и фактах компании.

- факт события или позиция банка со значением, которого нет в источниках, удаляются;
- риск или возможность с основанием «факт» или «позиция банка» понижаются до вывода модели;
- остальные утверждения помечаются, значение попадает в «Допущения и ограничения» и в замечания самопроверки, после чего агент один раз дорабатывает анализ;
- сроки в рекомендациях не проверяются: это предложения, а не факты.

`source_coverage` — доля значимых утверждений (факты, «почему важно», риски, возможности, действия, позиция банка), которые ссылаются на источник и не содержат неподтверждённых значений. Покрытие и результаты проверки показываются над анализом и агрегируются в `/analytics/quality` и в отчёте evaluation (`source_coverage`, `unverified_value_rate`).

### Дубликаты и обновления

- точный дубликат: тот же хеш содержания или нормализованный заголовок (регистр, «ё», пунктуация не важны) за 72 часа;
- то же событие в другом издании: близкие заголовки за ±48 часов с учётом синонимов («Банк России» = «ЦБ» = «Центробанк»). Противоположное направление («повысил»/«снизил»/«сохранил»), разные числа или разные участники дают разные события;
- та же ссылка с изменённым текстом — обновление публикации: содержание обновляется, классификация сбрасывается, анализ пересчитывается при следующем открытии;
- дубликаты сохраняются со ссылкой `duplicate_of`, но не попадают в ленту.

Сценарии покрыты тестами `internal/news/dedup_test.go` и интеграционным тестом.

## Быстрый запуск через Docker

Потребуется Docker с Compose. Go и Node.js на хосте не нужны.

### 1. Конфигурация

```bash
cp .env.example .env
```

Заполните:

| Переменная | Значение |
|---|---|
| `JWT_SECRET` | случайная строка не короче 32 символов, например `openssl rand -base64 48` |
| `LLM_API_KEY` | ключ OpenAI-совместимого шлюза организаторов |
| `POSTGRES_PASSWORD` | пароль PostgreSQL; можно оставить локальное значение из примера |

`DATABASE_URL` внутри Docker задаётся `docker-compose.yml`. Без `LLM_API_KEY` доступны лента, фильтры и локальное предварительное ранжирование, но недоступен полный персональный анализ.

### 2. Данные кейса

Положите предоставленные организаторами CSV в игнорируемую Git директорию:

```text
data/raw/df_Uid_data_hack.csv
data/raw/df_Uid_payment_hack.csv
data/raw/df_Fid_Uid_link_hack.csv
```

Подготовленные тексты аналитики банка находятся в `data/research/`.

### 3. Сборка и запуск

```bash
docker compose up -d --build
docker compose ps
```

Ожидаемый результат: `db` и `api` имеют статус `healthy`, `web` — `running`. Сайт доступен на <http://localhost:3000>, API — на <http://localhost:8080/api/>.

Compose публикует PostgreSQL на `localhost:5433`; внутри сети контейнеров используется `db:5432`.

### 4. Импорт

```bash
docker compose --profile import run --rm importer
```

Импортер загружает CSV, тексты аналитики и один раз опрашивает RSS. Он не вызывает LLM. Повторный запуск обновляет данные без создания URL-дубликатов.

### 5. Основной сценарий проверки

1. Откройте <http://localhost:3000> и зарегистрируйтесь.
2. Выберите роль, интересы и компанию в мастере онбординга.
3. На главной откройте персональную ленту и отсортируйте её по релевантности.
4. При необходимости нажмите «Оценить ленту моделью» — один запрос оценивает до восьми лучших кандидатов.
5. Откройте новость и запустите глубокий анализ.
6. Проверьте связь результата с компанией и ролью, риски, возможности, действия и позицию Альфа-Банка.
7. Перейдите по ссылкам на источники и раскройте «Как получен вывод»: план, источники, признаки компании, самопроверку и шаги.
8. В блоке «Спросить об анализе» нажмите «Какие признаки компании использованы?» и «Почему такая оценка?», задайте свой вопрос; повторите тот же вопрос — ответ придёт из кэша.
9. Оставьте оценку полезности анализа.
10. Нажмите круглую кнопку поддержки в правом нижнем углу и спросите, например, «Как сменить роль?».
11. Смените роль или параметры профиля и пересчитайте анализ, чтобы увидеть изменение персонализации.

## Модели и расход API

Код допускает только семейства из списка организаторов в `backend/internal/llm/allowed.go`. По умолчанию для всех структурированных этапов выбрана Gemma 4 26B A4B: на используемом шлюзе она стабильно завершает JSON-ответы. Разрешённую модель для каждого этапа можно изменить через `LLM_MODEL_FAST`, `LLM_MODEL_REASONING` и `LLM_MODEL_WRITER`.

| Переменная | Шаги |
|---|---|
| `LLM_MODEL_FAST` | классификация новости, «Оценить ленту моделью», ИИ-помощник поддержки |
| `LLM_MODEL_REASONING` | план анализа, самопроверка |
| `LLM_MODEL_WRITER` | персональный анализ и доработка, вопросы к анализу |

Модель вызывается только по явным действиям пользователя:

- «Оценить ленту моделью» — один запрос на пакет до восьми новостей;
- «Запустить анализ» — обычно 3–4 запроса, до 5 при доработке после самопроверки;
- уточняющий вопрос к анализу — один запрос; быстрые вопросы о признаках компании и подтверждённых фактах, а также повторы отвечаются без модели;
- вопрос ИИ-помощнику — один запрос; частые вопросы и повторы отвечаются по справке без модели.

Контроль расхода:

- `LLM_DAILY_TOKEN_BUDGET` — дневной бюджет токенов;
- `LLM_DAILY_CALL_LIMIT` — дневной лимит вызовов;
- `LLM_PER_MINUTE_LIMIT` — частота запросов;
- `ANALYZE_PER_USER_HOURLY` — число полных анализов пользователя в час;
- `ANALYSIS_QUESTIONS_PER_ANALYSIS`, `ANALYSIS_QUESTIONS_PER_USER_DAILY` — лимиты уточняющих вопросов к модели;
- `SUPPORT_QUESTIONS_PER_USER_DAILY` — лимит вопросов ИИ-помощнику;
- `LLM_MAX_OUTPUT_TOKENS` и лимиты каждого шага;
- кэширование одинаковых запросов и готовых анализов;
- объединение параллельных одинаковых запросов;
- пауза после HTTP 429, ошибки бюджета или отклонения ключа.

Резервный URL шлюза переключается вручную: измените `LLM_BASE_URL` в `.env` и пересоздайте API-контейнер.

## Evaluation на новых новостях

В `data/evaluation/` находится фиксированный синтетический holdout: 6 компаний разных отраслей, 25 ранее не использованных новостей, 4 роли, нерелевантный шум, неоднозначные события, профиль с неполными данными и межисточниковый дубль. Экспертная разметка задаёт проверяемые свойства результата, но не готовый текст ответа.

Безопасный offline-прогон не обращается к LLM:

```bash
cd backend
go run ./cmd/eval -data ../data/evaluation -mode mock -out ../evaluation-results/mock.json
```

Считаются Precision@K, Recall@K, NDCG@K, различие результатов для разных компаний и ролей (`differentiation_rate`), покрытие источниками и доля неподтверждённых значений (для live), совпадение тем, попадание score в диапазон, использование признаков компании, корректность `source_ids`, hallucination rate, JSON success rate, задержка, токены и оценочная стоимость. Mock является локальным baseline и проверяет CI-контур, а не качество LLM.

Live-прогон требует явного подтверждения и по умолчанию ограничен пятью кейсами:

```bash
set -a; . ./.env; set +a
cd backend
go run ./cmd/eval -data ../data/evaluation -mode live -confirm-live \
  -max-live-cases 5 -out ../evaluation-results/live.json
```

Предыдущий JSON-отчёт можно передать через `-baseline`, чтобы увидеть изменение метрик после новой версии промпта. Подробности — в `data/evaluation/README.md`.

## Мониторинг качества AI

Страница `/analytics/quality` и endpoint `GET /api/analytics/quality?period=30d` агрегируют уже сохранённые данные текущего пользователя и не вызывают LLM. Доступны периоды 7, 30 и 90 дней.

Мониторинг включает:

- success rate полных агентных запусков;
- ошибки JSON, обрезанные ответы, таймауты, ошибки ключа и ограничения провайдера;
- среднюю и P95-задержку, токены, число шагов и cache rate;
- долю анализов с фактами компании и позицией Альфа-Банка;
- прохождение самопроверки, количество revision-шагов и исправлений валидатора;
- среднее число источников, рисков, возможностей и действий;
- helpfulness rate по отзывам «Полезно / Не полезно»;
- уточняющие вопросы: доля ответов с опорой на источники, вызовы модели, кэш, ответы без модели, «нет в источниках», «вне рамок анализа»;
- статистику по моделям и версиям промпта;
- дневную динамику успешных и неуспешных запусков.

Метрики персональны: endpoint не раскрывает анализы или отзывы других пользователей. Комментарии feedback не отправляются в модель автоматически.

Рекомендуемый цикл сопровождения качества:

1. Собрать отрицательные отзывы и технические ошибки за период.
2. Проверить проблемные анализы и классифицировать причину: ranking, grounding, персонализация, полезность действий или UX.
3. Изменить правило, валидатор или промпт и увеличить `PromptVersion`.
4. Запустить offline evaluation и сравнить отчёт с baseline.
5. Выполнить ограниченный live evaluation при доступном бюджете.
6. Выпустить новую версию и наблюдать метрики по модели и `PromptVersion`.

Подробный порядок, включая проверку изменений, выкатку новой модели и откат, — в [docs/OPERATIONS.md](docs/OPERATIONS.md).

## Безопасность

- секреты находятся только в `.env`, который исключён из Git;
- LLM-ключ передаётся только backend в заголовке `Authorization` и не логируется;
- разрешённые модели проверяются перед каждым вызовом;
- пароли хранятся как Argon2id-хеши;
- JWT передаётся в HttpOnly cookie;
- для изменяющих запросов проверяется Origin;
- пользователь имеет доступ только к своим анализам, трассам и вручную добавленным новостям;
- инструменты агента выполняют ограниченные операции чтения внутри данных приложения;
- входы, ответы и списки ограничены по размеру;
- все значимые шаги и расход токенов журналируются без вывода секретов;
- текст вопросов пользователя изолирован в промптах от инструкций; ответы модели проходят детерминированную проверку по источникам или справке.

Как эти механизмы расположены в архитектуре — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#механизмы-безопасности-ai-компонентов).

## Ограничения прототипа

- внешние RSS-публикации СМИ анализируются по заголовку и анонсу: полный текст сохраняется только из лент, которые передают его сами и где это разрешено; полнота источника показывается пользователю;
- проверка фактов сверяет значения с источниками по совпадению чисел, дат и названий; перефразированные утверждения без чисел проверяет только LLM-самопроверка;
- качество зависит от полноты обезличенного профиля компании и доступных материалов;
- переключение на резервный LLM-шлюз выполняется вручную;
- offline-evaluation holdout и воспроизводимый CLI входят в репозиторий через `data/evaluation/` и `backend/cmd/eval`; вручного корпуса эталонных текстов ответов пока нет;
- интеграция входа из Альфа-Бизнеса и точка входа на главном экране интернет-банка представлены интерфейсом провайдера и кнопкой входа, а не реальным банковским SSO и виджетом;
- счётчики минутных и почасовых лимитов, кэш LLM и модель TF-IDF + LSA хранятся в памяти процесса API: для нескольких реплик их нужно вынести в общее хранилище (см. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#масштабирование)).
